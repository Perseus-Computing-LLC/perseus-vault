# Hostile Memory Gauntlet design

## Scope

The Gauntlet is a provider-neutral protocol for testing durable-memory
admission and retrieval boundaries under hostile conditions. It is adjacent to,
not a replacement for, the answer-facing LongMemEval work in #1164.

The evaluator grades:

- admission disposition and serveability;
- current versus superseded evidence identity;
- safe abstention versus wrong evidence;
- workspace scope and provenance preservation;
- deletion/tombstone behavior;
- bounded results/context; and
- duplicate replay materialization.

It does not generate answers or use an LLM judge.

## Threat families

The case schema supports forged quotes, stale corrections, out-of-order writes,
same-time authoritative conflicts, low-trust recency attacks, scope leaks,
foreign-only refusal, prompt injection, duplicate/near-duplicate floods,
terminology collisions, deletion, replay, provenance loss, irrelevant
distractors, Unicode/typo queries, and bounded-context pressure.

Each record is source-bound with a record digest, source reference, scope, actor,
trust class, validity interval, and recorded time. Cases and manifests are
independently hashed. Public projections reject raw text, queries, bodies,
provider payloads, credentials, and unknown/private fields.

## Result model

A probe observes `answer`, `abstain`, `blocked`, or `error`. Missing required
evidence is a miss. Returning forbidden, stale, foreign-scope, or unsupported
evidence is wrong. The report keeps `correct_evidence_rate`,
`safe_abstention_rate`, and `wrong_evidence_rate` separate, with stale and scope
leakage reported independently.

## Provider contract

```text
reset() -> None
ingest(record) -> AdmissionReceipt
forget(scope, record_id) -> MutationReceipt
retrieve(query, scope, as_of, limit) -> RetrievalResult
```

The contract is intentionally stronger than a generic `put/search` API:

1. Record identity is `(scope, memory_key, record_id)`; replaying a record ID is
   not a new admission.
2. Exact-content deduplication is scope-aware. The same text may exist in two
   isolated workspaces without becoming a cross-scope collision.
3. `supersedes` closes the older record's half-open valid-time interval, including
   when the older source arrives after its superseder. A later read must not
   resurrect stale evidence, while a historical read must retain provenance.
4. Hostile, conflicting, low-trust, duplicate, or near-duplicate writes are
   non-serveable (`quarantined` or `rejected`) and carry bounded reason codes.
5. Retrieval is scope- and validity-filtered, result-bounded, context-bounded,
   and provenance-bearing for every required hit.

An adapter may translate these semantics into backend-specific operations. It may
not silently drop a contract dimension and then report a pass. Unsupported
capabilities are explicit blocked/error evidence.

## Fixture validity and controls

The loader rejects impossible probes before provider execution. Required and
forbidden IDs must reference records in the case; required evidence must belong
to the requested scope; answer limits must fit the number of required records;
and answer probes need a positive context budget.

The repository includes `fixtures/public_cases.json`, a small synthetic control
suite generated by `fixtures/build_public_fixtures.py`. The reference provider
must pass all 14 cases / 15 probes. The naive provider is a deliberately unsafe
negative control and must complete but fail the release gate. These controls
prove harness discrimination; they are not a general provider leaderboard.

## Lifecycle

```text
case bundle + manifest -> run-return -> acceptance report
```

The runner records the manifest/case commitments and provider metadata. The
acceptance verifier recomputes case identity, metric aggregates, denominators,
public-boundary safety, and the report signature. `release_ready` requires a
complete passing run; accepted failed evidence remains useful for diagnosis but
cannot be promoted as a product gate.

## Real Vault reference integration

`gauntlet/perseus_mcp.py` is a provider adapter, not a raw Vault score shim. It
uses record-level Vault keys, adapter-side idempotency/admission guards, and
Vault's `valid_at` read primitive. Superseded records remain active with an
explicit closed valid-time interval so Vault's privacy-preserving temporal
serializer does not erase the provenance required by this contract. All real
runs use a fresh database per case and must prove process/database cleanup.

## Public/private separation

The repository contains the harness, schemas, generator, and small synthetic
control fixtures. It does not contain private holdout bodies or live provider
payloads. A private bundle belongs in a separate evaluation workspace and is
bound by the exact case-file SHA-256 in its manifest.

A locally authored private bundle can validate implementation behavior but is not
an independently blind split. General claims require a separately provisioned
or independently reviewed holdout, with raw case material kept outside Git and
outside public reports.
